# Публичный журнал состояния проекта — формат и канонический источник

## Канонический источник

Единственный редактируемый экземпляр журнала — **`data/project_log.json`** в
этом репозитории (`plekhanovmarket-stud.github.io`, публичный). Второй,
независимо редактируемой копии JSON не существует и заводить её нельзя.

`project-log.html` — только представление: он загружает `data/project_log.json`
через `fetch()` в браузере в момент просмотра (`Dash.loadAll(...)`, тот же
механизм, что и остальные страницы дашборда) и ничего не хранит захардкоженным.
Если когда-нибудь в HTML появится текст задачи/события, продублированный
вручную вместо рендера из JSON — это расхождение источника и отображения,
которое обязан ловить `scripts/validate_project_log.py` (приватный репозиторий
данных).

Это НЕ то же самое, что `data/changelog.json` / страница «Журнал изменений» —
тот журнал фиксирует изменения конкретных чисел и ручные корректировки
показателей. `project_log.json` — состояние ЗАДАНИЙ (поставлено/в работе/
принято/отклонено и т.п.), с приёмкой продукта, а не с числами дашборда.

## Структура файла

```
{
  "schema_version": 1,
  "log_id": "ozon-dashboard-project-log",
  "canonical_source": "...",              // текст, который показывается на странице как есть
  "note_scope": "...",                    // текст, который показывается на странице как есть
  "allowed_statuses": [...7 значений...], // должно ТОЧНО совпадать с утверждённым набором (см. ниже)
  "updated_at": "ISO 8601 с часовым поясом", // напр. "2026-09-07T15:25:14+05:00"
  "tasks": [ {...}, ... ]
}
```

`schema_version` обязан строго равняться поддерживаемому целому числу `1`
(`true`/`"1"`/`1.0`/любое другое значение — ошибка).

`updated_at` — не просто "меняется только при реальном изменении журнала", а
проверяется в ОБЕ стороны относительно опубликованной базы:
- если `tasks` изменились (появилось новое событие, изменилось состояние
  задачи и т.п.) — `updated_at` ОБЯЗАН измениться, иначе публикация
  блокируется ("тихое" изменение без обновления `updated_at`);
- если `tasks` не изменились — `updated_at` меняться не должен;
- `updated_at` не может быть раньше календарного дня самого позднего события
  во всём журнале.

Утверждённый набор `allowed_statuses` (порядок не важен, набор — точно этот,
без лишних/недостающих значений):
`поставлено` · `в работе` · `ожидает проверки` · `принято` · `принято частично`
· `отклонено` · `заблокировано`

### Задача (`tasks[]`)

| Поле | Обязательно | Смысл |
|---|---|---|
| `task_id` | да, не пусто | уникальный слаг, например `task-1` |
| `title` | да, не пусто | название |
| `date_opened` | да, не пусто | дата постановки — реальная календарная дата `YYYY-MM-DD` |
| `status` | да | один из `allowed_statuses` |
| `requirement_summary` | да | краткое описание требования |
| `done` | да | что выполнено |
| `remaining` | да | что осталось (текст, не пустая строка) |
| `last_updated` | да, не пусто | дата (`YYYY-MM-DD`) последнего события задачи — должна совпадать с календарным днём последнего события в `history[]` |
| `public_site_commit` | да (может быть `null`, если ещё нет) | git hash (7–40 hex-символов) коммита ПУБЛИЧНОГО репозитория сайта — обязателен (не `null`) при `status` ∈ {`принято`, `принято частично`}, ЕСЛИ ТОЛЬКО `remaining`/`done` не объясняют текстом (слово «отлож…»), что публикация сознательно отложена (приёмка содержания и публикация на production — разные события; сам факт приёмки не зависит от merge/публикации) |
| `private_data_commit` | нет | git hash (7–40 hex-символов) коммита ПРИВАТНОГО репозитория данных — только для внутренней трассировки, никогда не выдаётся как самостоятельное публичное доказательство |
| `public_evidence` | да (может быть `[]`, но не может быть пустым, если задача принята) | список `{type, label, url}`, см. ниже |
| `history` | да | список событий, см. ниже |

Если `status` ∈ {`принято`, `принято частично`} — в `history[]` обязано быть
хотя бы одно событие с `type: "приёмка"`.

### Доказательства (`tasks[].public_evidence[]`)

Каждый элемент — `{type, label, url}`, все три поля непустые. `url`:
- обязан начинаться с `https://` (никаких `http://`, `javascript:`, `data:`);
- домен обязан быть production-доменом сайта (`plekhanovmarket-stud.github.io`)
  или `github.com` — любой другой домен отклоняется проверкой;
- не может содержать `...` (фиктивная/усечённая ссылка);
- не может быть приватным data-коммитом, выданным за публичное доказательство.

### Событие (`tasks[].history[]`)

| Поле | Смысл |
|---|---|
| `event_id` | глобально уникальный (по всему файлу, не только внутри задачи) идентификатор, например `task-1-evt-3` |
| `date` | либо реальная календарная дата `YYYY-MM-DD` (без времени), либо, если есть время — **ISO 8601 с часовым поясом** (напр. `2026-09-05T23:10:36+05:00`). `YYYY-MM-DD HH:MM` без часового пояса — НЕ допускается. События внутри задачи должны идти по неубыванию календарного дня. |
| `type` | см. словарь ниже |
| `summary` | краткое описание события |
| `commits` | список строк вида `public:<hash>` (публичный site-коммит, проверяем ссылкой на GitHub) или `private:<hash>` (приватный data-коммит, только для трассировки — не публичное доказательство) |

Словарь `type` — значение проверяется СТРОГО по этому списку, любое другое
значение блокирует публикацию:

`поставлено` · `в работе` · `возврат_на_доработку` · `проверка` · `приёмка` ·
`публикация` · `примечание`

`commits` — поле ОБЯЗАТЕЛЬНО у каждого события (пустой список `[]`
допускается, отсутствие самого ключа — нет); каждый элемент обязан быть
строкой вида `public:<hash>` или `private:<hash>` (`<hash>` — 7–40
hex-символов).

## Неизменяемость истории

- Однажды опубликованное (закоммиченное в `origin/main`) событие в `history[]`
  — **не редактируется и не удаляется**. Исправление ошибочной записи — это
  НОВОЕ событие (например `type:"примечание"`, `summary:"уточнение к evt-N: ..."`),
  ссылающееся на старое по `event_id` в тексте.

### База сравнения — только `origin/main`

В штатной сборке (`build_all.py`) базой для проверки неизменяемости служит
**исключительно** `origin/main:data/project_log.json` — подтверждённая
опубликованная версия. Никакого автоматического отката на `HEAD` или на
что-либо ещё в штатном режиме нет. Перед сравнением ВСЕГДА выполняется
`git fetch origin main` — неудачный fetch сам по себе блокирующая ошибка
(локальный `origin/main` иначе может отставать от фактически опубликованного).

`HEAD` (или любой другой ref) используется как база **только** если он передан
явным параметром `base_ref` — а этот параметр существует исключительно для
ручного тестирования (`--base-ref HEAD` в CLI). Штатный вызов из
`build_all.py` этот параметр никогда не передаёт; при явном `base_ref` fetch
не выполняется.

### Bootstrap (первая публикация)

Признаётся ТОЛЬКО если одновременно доказано:
1. git-репозиторий доступен;
2. в штатном режиме — `git fetch origin main` прошёл успешно;
3. ref (`origin/main` в штатном режиме) существует;
4. `git ls-tree` этого ref **положительно подтвердил**, что пути
   `data/project_log.json` в дереве нет — само по себе отсутствие
   успешного чтения содержимого (`git show`) НЕ считается доказательством
   отсутствия файла.

Иными словами: если путь СУЩЕСТВУЕТ в дереве ref, но прочитать его содержимое
не удалось (`git show` завершился с ошибкой — например, объект блоба
недоступен) — это **блокирующая ошибка**, а не bootstrap. Раньше (до
исправления по независимой проверке V3) любая ошибка чтения трактовалась как
"файла нет", что позволяло ложно распознать повреждённую/недоступную базу как
первую публикацию.

Любая другая причина — git недоступен, `origin/main` не существует (нет
remote / не запушено / оборванная ссылка), JSON в базе повреждён, либо любая
иная невозможность прочитать базу — это **блокирующая ошибка**, а не
bootstrap. После того, как журнал был опубликован в `origin/main` хотя бы
один раз, bootstrap для этого репозитория больше невозможен: отсутствие
доступной базы в этот момент — всегда ошибка.

### Fail closed

Проверка `scripts/validate_project_log.py` останавливает сборку (`sys.exit(1)`
в `build_all.py`, до `publish_to_site()` и до `commit`/`push`) при любой из
следующих причин — предупреждения без остановки для них не допускаются:
- `data/project_log.json` отсутствует в рабочем дереве сайта;
- сам модуль `validate_project_log.py` не найден рядом с `build_all.py` или
  не импортируется;
- JSON повреждён / не соответствует структуре (см. таблицы выше);
- база сравнения (`origin/main`) недоступна по любой причине, кроме
  доказанного bootstrap.

## Правило приёмки

`status: "принято"` или `"принято частично"` может появиться в файле только
после явного решения Андрея в диалоге с Claude — сам факт успешной сборки,
пройденных проверок, `merge` или публикации сайта не является приёмкой и не
даёт Claude права самостоятельно проставить эти статусы.

## Что нельзя публиковать в этом файле

Токены/API-ключи, локальные пути (`C:\...`, `D:\...`, `/home/...`),
содержимое приватных исходных данных, персональные и коммерческие данные,
внутренние технические подробности автоматизации, не требуемые для публичной
приёмки (детали работы планировщика задач, механика служебных скриптов,
расположение и устройство секретов, внутренние блокировки и локальные
каталоги). `private_data_commit` — можно (это просто хэш, не раскрывающий
содержимое приватного репозитория), но нельзя называть его самостоятельно
проверяемым публичным доказательством.

## Связь со штатной сборкой

`build_all.py` (приватный репозиторий данных) копирует в `data/` сайта
ТОЛЬКО файлы из явного списка в `publish_to_site()`. `project_log.json` в
этом списке нет и не должно появляться — штатная сборка физически не
копирует в это имя файла и не может его перезаписать/удалить. Это
гарантируется структурой кода; регресс-тест на этот инвариант встроен в
`scripts/validate_project_log.py` и включён по умолчанию (отключается только
явным `--no-build-safety` при ручном запуске, штатная сборка его не передаёт).
