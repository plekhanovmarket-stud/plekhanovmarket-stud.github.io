Методология расчёта

Проверенные формулы (сверено с бухгалтерским файлом Кати до рубля) — менять только по явному запросу Андрея.

Термины (единые на всех страницах)

  • Реализовано — Ozon подтвердил продажу, используется в расчёте результата (источник: sale_amount, начисления) — главный дневной факт (решение Андрея 2026-09-05).
  • Заказано — оформлено покупателем, может быть отменено. Технически доступно через /v1/analytics/data, но ещё НЕ подключено к дневному прогону — см. «API-аудит» ниже. Историческое поле ordered в старых неделях — это НЕ «Заказано» (см. раздел ниже).
  • Операционная прибыль Ozon = Реализовано − Реклама − Прочее Ozon − Закупка.
  • Результат после расчётного НДС = Операционная прибыль Ozon − НДС (22/122).
  • Денежный результат после кредитов и расчётного НДС — действующая итоговая формула, до 2026-09-05 называлась «чистая прибыль» — сама формула не менялась, изменилось только название.
  • Факт — цифра прямо из источника или проверенного расчёта. Оценка — расчёт при неполных данных, всегда помечается визуально.

Налог на прибыль не считается и не показывается (решение Андрея, 19.08.2026, компания в убытке).

Заказано vs Реализовано — переоткрыто и исправлено 2026-09-05

Важная находка: поле orders_amount в /v3/finance/cash-flow-statement/list, которое до 2026-09-05 подписывалось как «Заказано», официально описано Ozon как «сумма цен реализованных товаров» — то есть это НЕ показатель с учётом отмен, а ещё один разрез того же «Реализовано» (по периодам cash-flow, не по дням). Расхождение ~3% между ним и sale_amount на 6 исторических неделях, найденное 2026-09-04, — это разница МЕТОДОВ подсчёта реализации (cash-flow-период vs сумма дневных начислений), а не «заказано включая отмены» против «реализовано». Терминология «Заказано»/«Реализовано» для этих недель была ошибочной — исправлена здесь и на странице «Продажи»; сами цифры (уже сверенные с файлом Кати) не менялись.

Ценообразование и маржа (страница «Цены и маржа»)

PCT = комиссия(sales_percent_fbo, живая) + эквайринг 1% + возвраты 4,13% + прочие услуги 3,95%.
FIX = себестоимость + логистика(факт или резервная тарифная таблица) + последняя миля + хранение(3% от себестоимости) + кросс-докинг(3,21% от закупки).
Безубыточная цена (целевой ДРР 5%) = FIX / (1 − PCT − 0,05).
Целевая цена (кредиты+ЗП+прибыль) = FIX / (1 − PCT − 0,05 − target_margin_pct).
Действие: qty=0 → «Нет продаж 28 дней»; цена < безубыточной → «Поднять цену»; маржа сейчас < 0 ≤ маржа при целевом ДРР → «Починить рекламу»; иначе «ОК». Целевой ДРР 5% — корпоративная цель, не меняется без согласования.

История цен (таблица «Было → Стало» на странице «Цены и маржа») ведётся скриптом track_price_history.ps1 с 2026-08-31 — более ранние изменения цены не восстановить, в Seller API нет метода с готовым логом цен.

Безубыточный ДРР по SKU (дополнение к ТЗ 2026-09-05, п.5)

Производный показатель от уже существующей экономики товара — НЕ замена корпоративной цели 5% (она используется как была, для безубыточной/целевой цены). Формула:
ads_безубыток = price × (1 − PCT) − FIX (максимальный расход на рекламу за единицу, при котором маржа сейчас ровно 0, при ТЕКУЩЕЙ цене)
безубыточный_ДРР% = max(0, ads_безубыток) / price × 100
Если price × (1 − PCT) < FIX — товар убыточен уже при нулевой рекламе (цена ниже безубыточной без рекламы вообще), безубыточный ДРР = 0, отмечается флагом «убыток без рекламы».

Проверено вручную на 3 SKU 2026-09-05: 11052DEK (цена 813 ₽, PCT 60,14%, FIX 246,26 ₽) → 813×(1−0,6014)−246,26 = 77,80 → 77,80/813×100 = 9,57%; 11053DEK (698 ₽, FIX 222,38 ₽) → 55,84 → 8,00%; 11054DEK (621 ₽, FIX 204,88 ₽) → 42,65 → 6,87%. Совпало с выводом функции построчно.

Очередь «Действия»

Один SKU даёт одно первичное действие: если у него уже есть рекомендация «Поднять цену», рекомендация по рекламе для того же SKU показывается как вторичная причина и не суммируется в общий эффект. Статус/ответственный/срок хранятся в config/actions_state.json (приватный репозиторий ozon-data) — не перезаписываются сборкой, редактируются вручную. Задачи, пропавшие из расчёта, не удаляются, а переходят в статус «устранено автоматически».

Дополнение к ТЗ 2026-09-04: ценовая рекомендация в статусе «новая» дольше 14 дней у SKU из топ-20 по обороту поднимается в начало очереди вне зависимости от денежного эффекта и помечается «просрочено».

Остатки: пороги «дней без продаж» (дополнение к ТЗ 2026-09-05, п.4)

Официальное описание поля days_without_sales (/v1/analytics/stocks) не указывает предел истории. Проверка 2026-09-05 по всем строкам сырых данных (8299 строк) показала фактический максимум 29 дней — ни одна позиция не превышает это значение. Пороги 30/60/90 дней из раздела 10.1 ТЗ на этом источнике сейчас недостижимы — показан реально доступный максимум (сейчас 29 дней, того же порядка, что и собственное окно qty_32d). Если это ограничение снимется в будущих выгрузках (появятся значения >29) — пороги 30/60/90 подключатся автоматически (см. build_inventory в lib_ceo.py: доступные пороги вычисляются от фактического максимума, не захардкожены).

Дни покрытия = остаток ÷ (продано за 32 дня / 32) — оценка, не факт; не считается для SKU без продаж за 32 дня (нет скорости продаж, на которую делить).

Продажи: штуки, ABC, рост/падение (дополнение к ТЗ 2026-09-05, п.2-3)

Утверждение «нет источника для штук» (из предыдущей версии) было неверным — sku_realization_32d.json содержит поле qty_sold по каждому SKU за 32 дня, тем же способом, каким планировщик всегда считал «продано за 32 дня». ABC по выручке строится по этому полю. ABC по прибыли — по margin_now_new × qty_32d, только для продающихся SKU с положительной прибылью (убыточные при продаже показаны отдельным счётчиком, не ранжируются внутри ABC).

Топ роста/падения по SKU сравнивает два периода: 28 дней до 2026-08-28 (снимок планировщика) и 32 дня до текущего прогона — периоды НЕ идентичны по длине (разница ~неделя), поэтому результат — оценка тенденции, не точный факт.

Как обновляется дашборд

Утро: PowerShell на компьютере Андрея собирает сырые данные из Ozon API, пушит в приватный репозиторий ozon-data. День: облачная рутина «Дашборд Ozon» (GitHub-webhook на пуш в ozon-data) считает все формулы скриптами (lib_pricing.py, lib_profit.py, lib_ceo.py, lib_changelog.py, build_all.py) и публикует готовые JSON в data/*.json публичного репозитория сайта. Никаких чисел вручную в HTML не вписывается.
